# ARPG Decision Atlas

This is ARPG's canonical product-intent tree. It consolidates **existing, owner-approved** direction from [ROADMAP](../ROADMAP.md), [ARCHITECTURE](../ARCHITECTURE.md), [AGENTS](../../AGENTS.md) and existing product issues, rather than treating code as a new product decision. Only **Decisions** and **Questions** are semantic entries; numbered headings are navigation. IDs are stable and must not be renumbered.

## Implementation evidence (retrospective pilot)

Child `- [x]` means **only the specifically named implemented capability** has cited source/test evidence. `- [ ]` means that particular behavior or verification remains outstanding. A checked technical foundation does **not** mean the complete parent Decision, public Pages experience or issue is finished. No checklist means *not audited*. These checklists do not create a third entry kind or an issue queue. Source paths plus symbols are durable pointers; tests and exact revisions establish evidence. The current `daq` indexer does not yet project child checkbox lines (see [coding-tooling #322](https://github.com/moritzbrantner/coding-tooling/issues/322) and [#323](https://github.com/moritzbrantner/coding-tooling/issues/323)).

- **1** Playable experience
  - **1.1** Undead crypt vertical slice
    - **1.1.1** [decision] A practical armored knight prepares before entering actual Rust-authoritative undead-crypt gameplay; real assets and honest loading are required, not a decorative mock. ([#145](https://github.com/moritzbrantner/arpg/issues/145))
      - [x] Local-game starting and saved character selection already exist: `web/src/character-selection.js::resolveCharacter`, `::persistSelectedCharacterId`, `web/src/main.tsx`; tested in `web/src/character-selection.test.js` ([current capability inventory](../../README.md)).
      - [x] WASM exposes real seeded gameplay creation: `crates/arpg-web-wasm/src/lib.rs::WasmGame::new_scenario` and `::advance_tick`.
      - [ ] Actual approved knight/weapon models and crypt entry/ready/failure journey have not passed the production-browser contract; acceptance is still draft ([#171](https://github.com/moritzbrantner/arpg/issues/171), [PR #160](https://github.com/moritzbrantner/arpg/pull/160)).
    - **1.1.3** [decision] Character models come from Quaternius Universal Base Characters with the free Modular Character Outfits – Fantasy kit, obtained only through the asset-tooling pipeline. The kit has no knight, so for now the knight wears the Male_Ranger outfit with pauldron; proper knight armour comes later ([asset-tooling #117](https://github.com/moritzbrantner/asset-tooling/issues/117)). No paid sources, ever. A pipeline-promoted asset (SHA-256-pinned source plus normal structural import checks) is approved; no byte-exact rebuild requirement. (Owner, 2026-10-17; [#145](https://github.com/moritzbrantner/arpg/issues/145#issuecomment-6232779971), [#55](https://github.com/moritzbrantner/arpg/issues/55), [asset-tooling #109](https://github.com/moritzbrantner/asset-tooling/issues/109), [#110](https://github.com/moritzbrantner/asset-tooling/issues/110))
    - **1.1.4** [decision] The preparation screen is where the player picks a savegame or creates a new, named character, and can create a multiplayer session to play with friends. Core and assets load there; the gameplay authority is created only on Start. The first run enters the existing seeded dungeon scenario with crypt presentation. (Owner, 2026-10-17; [#145](https://github.com/moritzbrantner/arpg/issues/145#issuecomment-6232779971))
    - **1.1.5** [decision] Saves: the Pages build keeps one Rust-validated record per character (name, progression, equipment) plus at most one in-progress run checkpoint in browser storage, with JSON export/import. The native build stores saves on the server (dedicated play) or locally in the native application. Every backend uses the same Rust-validated save document. Character names are core identity: validated in Rust, stored in saves and carried in snapshots. (Owner, 2026-10-17; [#172](https://github.com/moritzbrantner/arpg/issues/172), [#68](https://github.com/moritzbrantner/arpg/issues/68))
    - **1.1.6** [decision] Multiplayer from the preparation screen starts peer-hosted through `multiplayer-setup-service` (invite link, party lobby with names and ready toggles; the host's Start is enabled once everyone is ready and assets have loaded, then everyone enters together). Dedicated `game-server` sessions follow later. (Owner, 2026-10-17; [#173](https://github.com/moritzbrantner/arpg/issues/173), [#174](https://github.com/moritzbrantner/arpg/issues/174))
    - **1.1.7** [decision] The preparation journey ships as ordered slices: named knight + Start ([#171](https://github.com/moritzbrantner/arpg/issues/171)), then the saved-character list ([#172](https://github.com/moritzbrantner/arpg/issues/172)), then the peer session ([#173](https://github.com/moritzbrantner/arpg/issues/173)); #145 is superseded by these slices. (Owner, 2026-10-17)
    - **1.1.8** [decision] A character enters a run through `add_player(id, CharacterProfile { name })`; peer guests send the profile with their join, and dedicated play uses a server-assigned name until server-side characters arrive. Names are 1–20 characters after trimming (Unicode letters and digits, single spaces, apostrophe, hyphen), case-preserving and non-unique. The first slice ships once, with the real Quaternius knight; no temporary preview or presets. (Owner, 2026-10-17; [#171](https://github.com/moritzbrantner/arpg/issues/171))
    - **1.1.2** [decision] The Pages combat experience progresses from a physically shattering skeleton horde to an armored tactical duel and an executioner boss with victory/retry; independently test the real published game. ([#146](https://github.com/moritzbrantner/arpg/issues/146), [#147](https://github.com/moritzbrantner/arpg/issues/147), [#148](https://github.com/moritzbrantner/arpg/issues/148))
      - [x] Authoritative action phases, facing, telegraphs, staggers and defeat mechanics already exist in `crates/arpg-core/src/lib.rs` (named regressions `attacks_have_authoritative_commitment_active_and_recovery_phases`, `monster_attack_is_telegraphed_before_damage` in the [capability inventory](../../README.md)).
      - [ ] Real horde destruction, knight encounter, boss progression and published Pages visual acceptance have not been established by the existing core tests.
- **2** Authority and implementation boundaries
  - **2.1** One gameplay authority
    - **2.1.1** [decision] Deterministic combat, character and encounter outcomes belong to `arpg-core`; the browser, network adapter and 3D renderer consume outcomes rather than deciding them. ([architecture](../ARCHITECTURE.md), [#63](https://github.com/moritzbrantner/arpg/issues/63))
      - [x] The Rust-authoritative `crates/arpg-core/src/lib.rs` and `crates/arpg-web-wasm/src/lib.rs::WasmGame::apply_command` exist; movement/combat/snapshot tests are enumerated in the [current capability inventory](../../README.md).
      - [ ] This does not prove the intended real humanoid locomotion, integrated crypt animation and physical bone breakup on production Pages ([#55](https://github.com/moritzbrantner/arpg/issues/55), [#56](https://github.com/moritzbrantner/arpg/issues/56)).
  - **2.2** Reuse the same core across modes
    - **2.2.1** [decision] Local WASM, peer-hosted and dedicated play consume the same ARPG core commands and snapshot authority, with transport-specific delivery outside gameplay rules. ([architecture](../ARCHITECTURE.md), [#71](https://github.com/moritzbrantner/arpg/issues/71))
      - [x] Existing adapters: `crates/arpg-web-wasm/src/lib.rs::WasmGame`, `web/src/peer-session.js::attachPeerGameSession`, `crates/arpg-game-server/src/lib.rs` and `web/src/dedicated-session.js`; server/lane tests documented in [README](../../README.md).
      - [x] Aimed one-shot delivery carries validated aim through the correct command lane (`crates/arpg-core/tests/aimed_one_shots.rs`, `crates/arpg-core/tests/command_lanes.rs`, merged [PR #158](https://github.com/moritzbrantner/arpg/pull/158)).
      - [ ] Complete co-op session continuity and public gameplay parity remain in [#71](https://github.com/moritzbrantner/arpg/issues/71).
  - **2.3** Physics backend
    - **2.3.1** [decision] Until physics-engine is finished, ARPG's authoritative physics is **Rapier**, embedded in the Rust/WASM simulation; `arpg-core` keeps all gameplay outcomes. Each concrete gap or lesson from developing and playing with Rapier becomes a focused physics-engine issue, so it feeds back into completing physics-engine. The old integer `World` adapter is removed in the switching PR with no shim. (Owner, 2026-10-17; [#175](https://github.com/moritzbrantner/arpg/issues/175), supersedes [#48](https://github.com/moritzbrantner/arpg/issues/48) and [#162](https://github.com/moritzbrantner/arpg/issues/162))
    - **2.3.2** [decision] The Rapier integration uses full 3D `rapier3d` (f32) with default features: reproducible per build, no `enhanced-determinism`. Players and monsters move with Rapier's `KinematicCharacterController` on capsule colliders. f32 physics positions and velocities are authoritative and are rounded only for network and snapshots. Saves keep game state and rebuild the physics world on load; Rapier's own state goes into saves only once movable physics props exist. The save format changes once, with no shim. (Owner, live session 2026-10-17; [#175](https://github.com/moritzbrantner/arpg/issues/175))
- **3** Content and authoring
  - **3.1** Authoritative data definitions
    - **3.1.1** [decision] Use typed versioned content definitions for game-specific weapons, monsters, abilities and encounters; do not create gameplay authority inside the renderer. ([CONTENT](../CONTENT.md), [#73](https://github.com/moritzbrantner/arpg/issues/73))
      - [x] Versioned content bundle and validation exist in `crates/arpg-core/content/base.json`, `crates/arpg-core/src/content.rs`; tests include `base_content_reproduces_the_previous_tuning` and `saves_from_another_content_revision_are_rejected` ([README](../../README.md)).
      - [x] Seeded rooms/doors and encounter behavior exist (`crates/arpg-core/tests/dungeon_properties.rs`; `entering_combat_room_locks_connected_doors_until_encounter_is_cleared`).
      - [ ] A visually complete, reusable crypt presentation kit and owner-verifiable first adventure remain in [#72](https://github.com/moritzbrantner/arpg/issues/72) and [#145](https://github.com/moritzbrantner/arpg/issues/145).

  - **3.2** Character presentation
    - **3.2.1** [decision] Players appear as the released asset-tooling Ranger humanoid, loaded through 3d-lab's bundle loader (`adaptImportedCharacterBundle`) from the unpacked bundle. Setup downloads each released bundle once into the static `characters/` directory: no checksum, nothing committed, no runtime fetch from GitHub. The game starts once core and character are loaded, with byte progress and Retry. A flat ground ring under each character carries the action-phase, hurt, guard-broken, dead and focus-accent colours. The primitive shield board and bow box remain until the real sword and shield arrive ([#183](https://github.com/moritzbrantner/arpg/issues/183)). Textures ship uncompressed for now ([asset-tooling #257](https://github.com/moritzbrantner/asset-tooling/issues/257)). (Owner, live session 2026-10-17; [#55](https://github.com/moritzbrantner/arpg/issues/55), [3d-lab #132](https://github.com/moritzbrantner/3d-lab/issues/132))
    - **3.2.2** [decision] Character animation follows authoritative motion on the simulation timeline. Standing idles, a gait (walk, jog or sprint) is chosen by speed with stride-scaled playback, death plays once and holds, and changes crossfade. Attack, hurt, counter and bow clips wait for real clips ([asset-tooling #114](https://github.com/moritzbrantner/asset-tooling/issues/114)). The sword-drawn idle while engaged waits for the socket angle fix ([asset-tooling #113](https://github.com/moritzbrantner/asset-tooling/issues/113)). (Owner, live session 2026-10-17; [#188](https://github.com/moritzbrantner/arpg/issues/188), [#56](https://github.com/moritzbrantner/arpg/issues/56))
    - **3.2.3** [decision] Equipment presentation is data-driven: item kinds, sockets and loadout → socket mappings are data, so more items and attachment places, two-handed (multi-grip) weapons and left-handed characters need no overhaul. 3d-lab owns the generic joint attachment ([3d-lab #134](https://github.com/moritzbrantner/3d-lab/issues/134)); asset-tooling owns the shared socket and item descriptors ([asset-tooling #264](https://github.com/moritzbrantner/asset-tooling/issues/264)). Sword & shield go in the right and left hands; with the bow, the sword goes to the left hip and the shield to the back. The primitive bow box stays until a real bow exists. The guard board is removed in favour of the real shield, the guard clip and the ring colours. The slice ships only after the socket angle fix. (Owner, live session 2026-10-17; [#183](https://github.com/moritzbrantner/arpg/issues/183))
- **4** Input and controls

    - **4.1.2** [decision] A peer guest's held inputs are released as soon as its own connection to the host closes and reconnecting gives up, just like the dedicated "disconnected" state. (Owner, live session 2026-10-17; [#176](https://github.com/moritzbrantner/arpg/issues/176))
- **5** Traversal and combat physics
  - **5.1** Jumping and traversal ([#59](https://github.com/moritzbrantner/arpg/issues/59), [ADR 0002](../adr/0002-height-traversal-topology.md))
    - **5.1.1** [decision] #59's remaining scope ships as flat sub-issues, in order: walkable regions and typed connections ([#207](https://github.com/moritzbrantner/arpg/issues/207)), support on box tops, steps and ledges ([#208](https://github.com/moritzbrantner/arpg/issues/208)), ceilings ([#209](https://github.com/moritzbrantner/arpg/issues/209)), the overlapping bridge with a seeded A/B `traversal` workload ([#210](https://github.com/moritzbrantner/arpg/issues/210)) and fall recovery ([#211](https://github.com/moritzbrantner/arpg/issues/211)). Moving supports ([#212](https://github.com/moritzbrantner/arpg/issues/212)) stay a parked non-goal. Each physics-touching slice works on both `physics-ab` backends. (Owner, 2026-10-19)
    - **5.1.2** [decision] One walkable region per flat floor until elevation exists: the generated dungeon is a single region and doors are gated passages inside it, not region boundaries. (Owner, 2026-10-19; [#207](https://github.com/moritzbrantner/arpg/issues/207))
      - [x] `crates/arpg-core/src/topology.rs::Topology::single_floor` and region-local strikes, engagement, locks and interaction in `crates/arpg-core/src/lib.rs` (`ordinary_combat_targeting_and_interaction_are_region_local`, `an_actor_in_transit_stays_reachable_from_both_ends`).
    - **5.1.3** [decision] A player that falls out of the world respawns at its last supported position, with no damage. (Owner, 2026-10-19; [#211](https://github.com/moritzbrantner/arpg/issues/211))
      - [x] `crates/arpg-core/src/lib.rs::ArpgGame::recover_fallen_players` (`a_player_out_of_the_world_returns_to_its_last_supported_position_unharmed`, on both physics backends).
    - **5.1.4** [decision] Jump details from #191 stand: an action freezes horizontal motion mid-jump while gravity continues, every press is a full jump (no variable height), and hurt reactions do not block jumping. (Owner, 2026-10-19; [#191](https://github.com/moritzbrantner/arpg/pull/191))
  - **5.2** Melee physics ([#90](https://github.com/moritzbrantner/arpg/issues/90))
    - **5.2.1** [decision] The skirmisher's `monster.lunge` becomes a short multi-tick lunge that moves the attacker, resolved as a swept strike with per-strike target deduplication. (Owner, 2026-10-19)
      - [x] `crates/arpg-core/src/lib.rs::ArpgGame::resolve_monster_attack` with `MonsterLunge` (`a_lunge_catches_a_target_beyond_its_reach_once_along_its_path`, `a_lunge_into_a_thin_wall_stops_at_it_and_is_obstructed`, on both physics backends).
    - **5.2.2** [decision] Damageable props are static crates with health and no drops, placed in combat rooms; they block movement and navigation until broken. Strike rays exclude the struck body through the `Physics` seam on both backends. (Owner, 2026-10-19)
      - [x] `crates/arpg-core/src/lib.rs::place_crates`, `::ArpgGame::damage_crate` and `Physics::segment_obstructed_except` (`strikes_break_a_crate_which_then_stops_blocking_and_drops_nothing`, `a_segment_can_ignore_one_static_body_but_not_the_others`, on both physics backends).

## Issue handoffs

Product intent remains here. GitHub issues should form a mostly **flat queue of small, verifiable slices**, not persistent nested epics. Close a too-large issue with an explicit successor handoff, marking it superseded rather than completed if its original acceptance did not pass. One active implementation worker per repository; independent acceptance authorship and implementation occur sequentially. Do not create duplicate work already covered by the tests and source above.
